# Security review — BoxLite Micro-cloud prototype

Read-only review of `control-plane/` (TS/Hono/sqlite), `supervisor/` (Go) and `cli/`, against the
four-attacker threat model in the brief: (a) anonymous internet, (b) signed-in end user of one app,
(c) a coding agent holding app A's key, (d) malicious code inside app A's Box.

Scope note: no code was modified. A local CP was reasoned through rather than run against live infra.
Line references are to the tree as reviewed.

## Findings

Ranked by severity.

| id | sev | area | finding | how to exploit | fix (file / function) | test to add |
|----|-----|------|---------|----------------|-----------------------|-------------|
| F1 | **critical** | proxy / origin isolation | **All apps and the console share one origin.** Any app can script that origin: a stored/reflected XSS in app A, or simply a malicious app hosted on the platform (attacker (c)), runs JS on `https://<cp>`. The console API lives at `/console/api/*` on the same origin and is gated only by the `bxl_console` cookie (`Path=/console`) plus a same-origin `Origin` check (`console-auth.ts crossSite`). Same-origin `fetch('/console/api/...', {credentials})` from app A sends the admin's console cookie and passes `crossSite` (same host). App A JS can therefore create/delete apps, rotate keys, run SQL against **any** app, publish/visibility-change, etc. The same JS can also read any **other** app the victim is signed into: `fetch('/appB/…')` carries app B's `bxl_cp_session`/`bxl_s_appB` (HttpOnly stops reading the cookie, not sending it). | Host a BoxLite app that serves `fetch('/console/api/apps',{method:'POST',headers:{'content-type':'application/json'},body:'{"name":"evil"}'})`; get any console admin to open the app in the same browser. Or exploit an XSS in a victim app and pivot to `/console/api/*` and `/<otherapp>/`. | Separate origin per app (wildcard domain `*.apps.<cp>`), and put the console on its own host. Until then: serve the console from a distinct origin, keep app traffic off the console origin, and keep every CP cookie `HttpOnly` (already true). Add a per-request CSRF token to `/console/api/*` (`console-auth.ts requireConsoleApi`) that app-origin JS cannot read. | `console.test.ts`: a request to `/console/api/apps` whose `Origin` is the CP host but whose path was reached from an app prefix must be rejected / must require a CSRF token. |
| F2 | **high** | supervisor / attacker (d) | **In-Box app code can read the gateway secret and box token and impersonate any end user.** `deploy.FilteredEnviron` strips `BOXLITE_BOX_TOKEN`/`BOXLITE_CP_URL`/`SV_*` from *service* env, but the supervisor process keeps them in its own environ (`/proc/<sv pid>/environ`, same uid) and `state.json` stores `gateway_secret` + the full resolved env (DATABASE_URL, secrets) at mode 0600 **owned by the same uid app code runs as**. Every app Box runs with `SV_TRUST_USER_HEADERS=1` (`resources.ts ensureBox`), so the gateway forwards `X-BoxLite-User-*`/`X-BoxLite-Identity` whenever the gateway secret is present. App code can read the secret from `state.json`, then `POST http://127.0.0.1:8080/<any path>` with `X-BoxLite-Gateway: <secret>` + `X-BoxLite-User-Id: <victim>` and spoof **any** end user to its own service. With the box token it can also call the CP `/sv/v1/*` to post fake deploy status/logs for its own env. | Inside the Box: `secret=$(jq -r .gateway_secret /home/boxlite/app/state.json); curl -H "X-BoxLite-Gateway: $secret" -H 'X-BoxLite-User-Id: <admin-uuid>' http://127.0.0.1:8080/admin`. | The gateway's loopback forwarding and the end-user identity injection trust the same secret the app can read. Mint a **separate** inbound-identity credential the CP holds and the app cannot read, or sign identity headers (the RS256 identity JWT already exists — have the gateway *verify* `X-BoxLite-Identity` instead of trusting raw `X-BoxLite-User-*`, and drop `SV_TRUST_USER_HEADERS`). Run services under a different uid than the supervisor/state dir. (`gateway.go rewrite`, `main.go`, `resources.ts ensureBox`) | `gateway_test.go`: with trustIdentity on, a request carrying the secret + `X-BoxLite-User-*` but no valid signed identity is stripped. |
| F3 | **high** | supervisor gateway | **One secret does two jobs, so the CP path check is the only thing keeping end users off the control API.** The proxy attaches `X-BoxLite-Gateway` to *every* forwarded end-user request (`proxy.ts forward`), and the gateway accepts control calls (`/.boxlite/sv/deploy|activate|rollback|restart`) from anything carrying that secret (`gateway.go ServeHTTP`). The sole barrier against an end user reaching the control API is the CP's normalised `/.boxlite/` block (`enduser-auth.ts identityFor`). A raw-vs-normalised divergence (the block uses `normalisePath`, but `forward` sends the raw `p.rest`) would expose deploy/rollback/restart to attacker (a)/(b). No concrete bypass was found (the normaliser decodes `%xx`, collapses `//`, resolves `..`, lower-cases), but the design is one parser bug away from RCE-class control. | Any end-user path that the JS normaliser treats as non-control but Go's `r.URL.Path` resolves to `/.boxlite/sv/deploy` would be forwarded with the secret attached and executed. | Don't attach the control secret to proxied end-user traffic. Give the gateway a dedicated control path/credential the proxy only sets for genuine `/.boxlite/sv/*` CP calls, and have end-user forwarding use a header the gateway never treats as control. (`proxy.ts forward`, `gateway.go control`) | `proxy.test.ts` + `gateway_test.go`: a matrix of encoded `.boxlite` paths (`%2e`, `%2f`, `..`, mixed case, trailing dot) must all 404 at the CP and never reach `control`. |
| F4 | medium | end-user auth / JWT | **Identity JWT is not audience-bound to the app that must accept it.** `identityToken` (`enduser-auth.ts`) signs with one platform-wide RS256 key and publishes it at a shared `/auth/jwks.json`. Claims carry `app`/`env` but nothing forces an app to check them, and a token for app A is a validly-signed, `iss`-valid token everywhere. A malicious app A that receives a user's `X-BoxLite-Identity` can replay it to app B's API; if app B verifies only signature+`iss` (the natural implementation) it accepts app A's user as its own. | App A captures `X-BoxLite-Identity`, replays to `https://<cp>/appB/api` (or app B's own token-verifying endpoint). | Put the app prefix in the JWT `aud` and document that apps MUST verify `aud`/`app`+`env`; or sign each app's identity tokens with a per-app key exposed only at that app's JWKS. (`enduser-auth.ts identityToken`, `jwks`) | `enduser-auth.test.ts`: a token minted for app A fails an `aud`-checking verify for app B. |
| F5 | medium | SQL endpoint | **`BEGIN TRANSACTION READ ONLY` does not stop side-effecting functions, and the app DB role is the Neon owner.** `classify` (`sqlguard.ts`) blocks tx-control, `COPY`, `SET ROLE/…`, and DDL by first keyword, but a read query may call functions with side effects: `SELECT pg_sleep(14)` (DoS up to the 15s `statement_timeout`), `SELECT pg_terminate_backend(pid)`, and—because the role is `neondb_owner` (`neon.ts ROLE`)—owner-only functions (`pg_read_file`, `lo_import`, `adminpack`). `DO $$…$$` blocks also bypass the DDL keyword classifier (keyword `DO`); on non-main with `write:true` they execute arbitrary PL/pgSQL incl. DDL the "DDL needs write" rule never inspects. Blast radius is the app's own Neon branch, but owner rights are broader than the SQL console intends. | With an app key (or console), `POST /db/sql {"query":"SELECT pg_terminate_backend(pid) FROM pg_stat_activity"}`, or `{"query":"DO $$ BEGIN PERFORM pg_sleep(14); END $$"}`. | Give apps a least-privilege Neon role (not the branch owner); deny side-effecting/admin functions; treat `DO` as DDL in `classify`; cap result buffering (see F8). (`neon.ts`, `sqlguard.ts classify`, `routes/db.ts`) | `sqlguard` unit test: `DO $$…$$` is classified `ddl=true`; `routes/db.ts` test: `pg_sleep`/`pg_terminate_backend` refused or role-blocked. |
| F6 | medium | blobs / tenancy | **Content-addressed blobs are global, giving a cross-tenant existence oracle and content-exfil path.** `BlobStore` is shared by all apps; `POST /uploads` returns `missing[]` = hashes not already present (`routes/uploads.ts`). App A can probe whether a file with a given sha256 exists anywhere on the platform, and if it knows the hash it can list that file in its own manifest, skip the upload (dedup), `complete`, and download the other tenant's bytes via its own `deployments/{n}/source`. | App A uploads a manifest claiming `path=x, sha256=<hash of app B's secret>`; `missing` omits it → `complete` → fetch snapshot tar → read B's content. | Namespace blob existence per app (track ownership; a hash "present" for app A only if app A uploaded it), or require the uploader to actually stream bytes even on dedup. (`blobs.ts has/put`, `routes/uploads.ts`) | `uploads` test: app B cannot `complete` a snapshot referencing a blob only app A uploaded. |
| F7 | medium | proxy / `?__key=` | **The one-time App key travels in the URL.** `?__key=<App key>` (`proxy.ts proxyHandler`) lands in browser history, any upstream/CDN/proxy access log in front of the CP, and the `Referer` of the first response's sub-resources before the 302 strips it. The CP's own access log scrubs it (`console-access.ts`) and the CP redirects to drop it, but the raw inbound request still carried it. A leaked App key is full CLI authority over the app. | Capture the first `/<app>/?__key=…` request at any hop in front of the CP, or read it from the victim's history. | Prefer the console "Open app" hop (already implemented) and deprecate `?__key=`; if kept, accept it only via `POST`/header, and set `Referrer-Policy: no-referrer` on the redirect. (`proxy.ts proxyHandler`) | `proxy.test.ts`: `__key` responses send `Referrer-Policy: no-referrer` and never appear in forwarded headers (already true) nor logs. |
| F8 | medium | resource abuse | **Unbounded result buffering and no ingest/subscriber caps.** `PgAppDatabase.query` (`appdb.ts`) buffers the full result set in memory before `slice(0, MAX_ROWS)` — a `SELECT` over a huge table OOMs the CP before truncation. `/sv/v1/logs` accepts 5000 lines/request with no per-box rate limit (`routes/sv.ts`), a compromised box can spin CPU/IO (ring trims storage to 20k but not ingest cost). SSE endpoints (`routes/logs.ts`, `routes/deployments.ts`) have no per-env/connection cap. | A compromised box POSTs log batches in a tight loop; or an app key runs `SELECT * FROM big_table`. | Use a server-side cursor / `FETCH FIRST n+1` to bound rows; rate-limit `/sv/v1/logs` per box token; cap concurrent SSE subscribers per env. (`appdb.ts query`, `routes/sv.ts`, `routes/logs.ts`) | `appdb` test: a query returning > MAX_ROWS never materialises more than MAX_ROWS+1 rows. |
| F9 | low | proxy / cookies | **`rewriteSetCookie` rescopes `Path` but not cookie name or `Domain`.** An app can emit `Set-Cookie: bxl_console=…` or `bxl_s_<x>=…`; the name collides with CP cookies (different `Path`, so not an override today, but brittle), and a `Domain=` attribute is passed through unchanged. | App B sets a cookie named like a CP cookie to confuse `getCookie` parsing. | In `rewriteSetCookie` (`proxy.ts`) refuse/namespace reserved cookie names (`bxl_*`) and strip `Domain`. | `proxy.test.ts`: an upstream `Set-Cookie: bxl_console=…` is dropped or renamed. |
| F10 | low | org key blast radius | **Volume cleanup scans all org volumes and deletes by name prefix.** `deleteVolumes` (`resources.ts`) lists every volume in the org and removes those matching `mc-<app>-<env>-`; a name collision from another resource in the shared dev org would be deleted. Boxes are otherwise addressed by recorded id (good). | Low — names are CP-generated; relies on the shared dev org never colliding. | Record created volume ids on the env and delete by id only (as Boxes already are). (`resources.ts deleteVolumes`, `ensureBox`) | `orchestrator`/resources test: deletion targets only recorded volume ids. |

## What's done well

- **No path from a Box to org-level secrets.** `createBox` (`resources.ts`) injects only `BOXLITE_CP_URL`, `BOXLITE_BOX_TOKEN`, `BOXLITE_ENV_ID`, `SV_TRUST_USER_HEADERS`. The BoxLite org key, Neon key, GitHub client secret and admin token live only in the CP's `cp.env` and are never shipped to a Box. A compromised supervisor/app cannot escalate to them.
- **Keys are stored hashed.** App keys, box tokens and end-user session tokens are kept as `sha256` only (`auth.ts`, `enduser-auth.ts createSession`); the clear value is shown once. Admin-token and session-MAC comparisons are `timingSafeEqual` (`auth.ts safeEqual`, `console-auth.ts`, `verifySession`).
- **Box-token scoping holds.** `/sv/v1/spec|snapshots|logs|status` resolve env/app from the token (`auth.ts requireBoxToken`, `routes/sv.ts`); env X's token cannot fetch env Y's spec or snapshot.
- **Tar extraction is hardened.** `release.Extract` rejects absolute names, `..` escapes, symlink/hardlink targets that resolve outside the root, and device/fifo entries (`supervisor/internal/release/release.go`).
- **Static serving is careful.** Dotfiles blocked, cleaned paths, and a real `EvalSymlinks` within-root check (`supervisor/internal/gateway/static.go`).
- **Upload validation.** Relative/normalised path checks, per-file and total size caps, and sha256 verification on store with atomic rename (`routes/uploads.ts`, `blobs.ts put`).
- **OAuth flow.** PKCE S256 + HMAC-signed `state` bound to a verifier cookie, strict `safeNext` (no scheme/`//`/backslash/dot-segments, decoded), blocked-user revocation, and CSV formula-injection escaping (`enduser-auth.ts`).
- **Proxy hygiene.** Inbound `X-BoxLite-User-*`/`X-BoxLite-Identity`/`X-Forwarded-*` and the CP session cookies are stripped before forwarding; `Location`/`Set-Cookie` are rescoped to the app prefix; `.boxlite/` is blocked for end users (`proxy.ts`, `enduser-auth.ts identityFor`).
- **SQL defence-in-depth.** Read-only transaction + pg extended protocol (one command per message) blocks multi-statement smuggling; secret files are written `0600` (`config.ts persistentSecret`, `enduser-auth.ts signingKey`).
